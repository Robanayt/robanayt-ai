# Holographic Desktop UI — архитектурное предложение

**Статус: предложение. Ничего не реализовано.** В пакете `jarvis/` нет ни
одного GUI-модуля, GUI-зависимости не добавлены, `pyproject.toml` не изменён
(`dependencies = []` остаётся пустым). Документ описывает границы, интерфейсы
и порядок работ — для принятия решения, а не для реализации.

Дата: 2026-10-29. Платформа: Windows, Python 3.14.10, 16 GB RAM.

---

## 1. На что опирается предложение (проверенные факты проекта)

| Факт | Источник |
|---|---|
| Слои: `core → ai → memory → tools → orchestration → app`; зависимости односторонние | `jarvis/__init__.py`, `STATUS.md` §1 |
| `DialogService`: `send()`, `approve_pending(id)`, `cancel_pending(id)`, `pending()`, `describe()`, `close()` | `jarvis/orchestration/service.py` |
| Шина событий уже есть: `APP_STARTING/RUNNING/STOPPING/STOPPED`, `TOOL_EXECUTED`, `TOOL_BLOCKED` | `jarvis/core/bus.py:30-33`, `jarvis/tools/audit.py:30-31` |
| Один вызов CLI — один ход; коды выхода `0/2/3/4/5/6/7`; интерактивного цикла нет | `jarvis/app.py`, `STATUS.md` §9 |
| Ограничение одного экземпляра — файловый lock с PID | `jarvis/core/single_instance.py` |
| Режимы запуска: normal / safe / diagnostic / development (политика пока не применяется в композиции — F-02) | `jarvis/core/run_mode.py` |
| Внешних зависимостей у рантайма нет; тесты — только `pytest` | `pyproject.toml:13-16` |
| Native tool calls: провайдеры заполняют `metadata["tool_call"]` | `jarvis/ai/tool_calls.py`, `STATUS.md` §18.1 |

Ключевое следствие: **ядро уже завершено и самодостаточно**. UI не должен
владеть ни базой, ни провайдером, ни реестром инструментов — только
отображать состояние и передавать команды.

## 2. Принципы

1. **Ноль новых рантайм-зависимостей.** Ни PySide6, ни Electron, ни pystray.
   Всё, что требует установки, — отдельное решение пользователя.
2. **UI — доверенная поверхность, но не источник разрешений.** Право на
   выполнение даёт только `approve_pending()` существующего оркестратора;
   UI не может обойти политику, добавить инструмент или выдать токен.
3. **Данные модели и инструментов — данные.** Всё, что приходит от модели,
   памяти или результата инструмента, отображается как данные, а не как
   инструкции (уже так работает в оркестраторе).
4. **Ядро не зависит от UI.** `jarvis.surfaces` (если появится) зависит от
   ядра, а не наоборот. Без UI приложение продолжает работать как сейчас.
5. **Один процесс, один экземпляр.** UI не снимает файловый lock и не
   порождает фоновых агентов.

## 3. Варианты реализации

| Вариант | Суть | Плюсы | Минусы / риски |
|---|---|---|---|
| **A. Локальный веб-интерфейс на stdlib** | `http.server` (или `socketserver`) в отдельном потоке + `webbrowser` для открытия; «голографический» вид — HTML/CSS/JS, без сборки | 0 зависимостей; кроссплатформенно; быстрый прототип; изоляция в браузере пользователя | нужен аккуратный разбор углы: привязка только к `127.0.0.1`, защита от CSRF/подмены origin, корректное завершение потока |
| **B. Нативный Win32 (ctypes)** | трей/окно/оверлей через `ctypes` + `user32`/`shell32` | 0 зависимостей; «настоящий» desktop-вид, оверлей поверх окон | только Windows; много низкоуровневого кода; риск блокировки цикла сообщений; сложнее тестировать |
| **C. Внешний фреймворк** (PySide6 / Qt / Electron) | классический GUI | привычные инструменты, rich-виджеты, анимации | ломает принцип «0 зависимостей»; десятки/сотни МБ; тянет обновления и лицензии; противоречит текущей границе фазы |

**Рекомендация для обсуждения:** начать с **A** (максимум эффекта при нуле
зависимостей), оставив транспорт абстрактным, чтобы вариант **B** можно было
добавить позже как альтернативную поверхность. Вариант **C** — только по
отдельному решению пользователя.

## 4. Предлагаемая архитектура

```
jarvis/
  core/  ai/  memory/  tools/  orchestration/     ← без изменений
  surfaces/                                       ← новый слой (план)
    protocol.py    сообщения UI ↔ ядро (dataclass'ы, JSON-совместимые)
    bridge.py      единственная точка, где UI вызывает ядро
    web/           транспорт варианта A (http.server, статические файлы)
    win/           транспорт варианта B (только если выбран)
```

### 4.1 Интерфейс `surfaces/bridge.py` (проект, без кода)

```
DialogBridge(dialog: DialogService, tools: ToolSystem, bus: EventBus)

    # команды (UI → ядро)
    send_message(text, *, conversation_id=None) -> TurnView
    approve(pending_id) -> TurnView
    cancel(pending_id) -> bool
    snapshot() -> StateView          # состояние для отрисовки

    # события (ядро → UI)
    subscribe(listener) -> unsubscribe
```

`TurnView` / `StateView` содержат **только** то, что уже безопасно наружу:
статус хода, ответ, список `tool_calls` (имя, статус, `execution_id`, причина),
`pending` (имя инструмента и аргументы — как в CLI, для осознанного согласия),
счётчики, `persisted`, `context_truncated`. Ни секретов, ни полных
провайдерных ответов, ни трассировок.

### 4.2 Протокол (вариант A)

- Транспорт: HTTP на `127.0.0.1`, случайный свободный порт, одноразовый
  токен в заголовке/query; окно открывается существующим браузером.
- Канал состояния: короткий polling (`GET /state`) или SSE через stdlib
  (`text/event-stream`) — без внешних библиотек.
- Команды: `POST /turn`, `POST /approve`, `POST /cancel` с проверкой токена и
  `Origin`/`Host`.
- Остановка: сервер — daemon-поток, останавливается по `APP_STOPPING`.

### 4.3 Потоки

- Ядро остаётся в основном потоке (как сейчас в CLI).
- Сервер UI — фоновый поток(и); вызовы ядра сериализуются.
- ⚠ **Открытый вопрос**: `EventBus.publish()` не документирован как
  потокобезопасный. Нужен либо мьютекс в `bridge`, либо очередь событий,
  которую основной поток опустошает. Требуется решение до реализации.

## 5. Безопасность

| Риск | Мера |
|---|---|
| Доступ к UI из другой машины | привязка только к `127.0.0.1`, проверка `Host`/`Origin`, одноразовый токен, закрытие порта при выходе |
| CSRF / посторонние вкладки | токен + `SameSite`, отклонение запросов без токена, запрет `GET` для изменяющих команд |
| Подмена роли «доверенной поверхности» | UI вызывает только `approve_pending()` / `send()`; токен подтверждения создаётся исключительно в `jarvis.tools.policy` |
| Утечка значений аргументов | аргументы показываются только в карточке подтверждения (как сейчас в CLI); аудит и `describe()` значений не содержат |
| Prompt injection через ответ/инструмент | результат инструмента и ответ модели — данные; разметка экранируется, HTML не исполняется как инструкция |
| Зависание UI из-за долгого хода | ход ограничен (≤3 вызова, ≤`limit+1` запросов); UI показывает состояние «ходит», таймауты инструментов — кооперативные (существующее ограничение F-08) |
| Секреты | ключи провайдеров не попадают в UI; в конфигурации хранятся только имена env-переменных |

## 6. Порядок работ (предложение)

| Шаг | Содержание | Зависимости |
|---|---|---|
| **S1** | `surfaces/protocol.py` + `bridge.py`: типы сообщений, вызовы существующего API, тесты без транспорта | ничего |
| **S2** | Локальный транспорт варианта A: `http.server`, статические файлы, SSE/polling, тесты на loopback | S1 |
| **S3** | Каркас интерфейса: состояние, список ходов, карточка подтверждения | S2 |
| **S4** | «Голографическая» стилизация: CSS/анимации, без зависимостей | S3 |
| **S5** (опция) | Трей/оверлей Win32 (`ctypes`) как альтернативный транспорт | S1, отдельное решение |

Ни S1–S5 не требуют изменения ядра, кроме добавления слоя `surfaces/`.
Любое изменение ядра (например, потокобезопасность шины) — отдельная задача с
регрессионными тестами.
