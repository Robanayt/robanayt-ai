## 1. Архитектура оркестрации (Фаза 5)

```
jarvis.orchestration.DialogService(ai, memory, tools, OrchestrationConfig)

    send(message) ->  resolve/create conversation
                      limited context from memory
                      AIService.generate()
                      protocol: structured tool call (metadata) or
                                fenced-JSON block (opt-in)
                      ToolExecutor.execute()  -> policy checked here
                      feed the result back as untrusted data
                      final answer -> persist
    approve_pending(id) -> grants one approval, resumes the turn
```

Слой оркестрации не владеет базой, провайдером или реестром: он
переиспользует `AIService`, `MemoryService` и `ToolSystem`. Зависимости
односторонние: `jarvis.orchestration` → `jarvis.ai` / `jarvis.memory` /
`jarvis.tools` / `jarvis.core`. Циклических импортов нет (проверено 2026-10-29:
импорт всех **47** `.py`-модулей пакета по отдельности — `47 OK / 0 fail`).

## 3. Ограниченный цикл вызовов инструментов

- Максимум `max_tool_calls_per_message` выполнений на одно сообщение
  (по умолчанию **3**, верхняя граница **10**).
- Соответственно максимум `limit + 1` запросов к модели за ход.
- Бесконечных циклов нет: при исчерпании лимита ход останавливается со
  статусом `tool_limit_reached`, ответ не выдумывается.
- Инструмент вне реестра не запускается (`tool_error`, запись `not_found`).
- Модель не подтверждает свои вызовы: `send()` не имеет параметра
  подтверждения; `bridge.tool_call_from_ai()` отклоняет поля `approved`,
  `permission`, `force`, `bypass`, `sudo` и т. п.
- Перед каждым выполнением работает политика Фазы 4; подтверждение
  привязано к имени, версии и дайджесту аргументов, одноразовое.
- Автоматических повторов нет: упавший инструмент останавливает ход
  (`tool_error`), обработчик вызывается ровно один раз (покрыто тестом).
- Текстовый ответ модели не считается выполнением инструмента.

## 4. Каналы вызова инструмента

| Канал | Состояние | Формат |
|---|---|---|
| Структурированный | всегда включён | `AIResponse.metadata["tool_call"] = {"name": ..., "arguments": {...}}`; заполняется нативно из `tool_calls` провайдеров Ollama и OpenAI-compatible (`jarvis.ai.tool_calls`) |
| Текстовый | `allow_text_tool_calls = false` по умолчанию | единственный блок ```` ```json ```` с одним ключом `tool_call` |

Обычная проза («я мог бы сложить 2 и 2») никогда не считается вызовом.
Невалидный явный блок — это ошибка `invalid_tool_call`, а не попытка
угадать намерение. Оба канала валидируются одним и тем же
`jarvis.tools.bridge`, а выполняются одним и тем же `ToolExecutor`.

## 5. Статусы хода

| Статус | Значение |
|---|---|
| `success` | ход завершён, `answer` — ответ ассистента |
| `approval_required` | ход остановлен, инструмент ждёт подтверждения (`pending`) |
| `tool_limit_reached` | лимит вызовов исчерпан, ответа нет |
| `invalid_tool_call` | явный вызов не прошёл валидацию, ничего не выполнено |
| `ai_error` | ошибка провайдера / AI отключён |
| `memory_error` | память недоступна (например, диалог не найден) |
| `tool_error` | инструмент не найден, запрещён или не выполнился |
| `empty_response` | модель вернула пустой ответ (успехом не считается) |
| `pending_expired` | подтверждение не найдено или просрочено |
| `disabled` | оркестрация отключена конфигурацией |

`DialogResult` содержит: `answer`, `conversation_id`, `tool_calls`,
`tool_call_count`, `pending`, `error` (без трассировок), `error_type`,
`persisted`, `persist_error`, `memory_enabled`, `context_truncated`,
`provider`, `model`. Ни трассировок, ни секретов, ни полных
провайдерных ответов наружу не выдаётся.

## 6. Память и контекст

- Диалог создаётся при первом сообщении или продолжается по явному
  `conversation_id`; отсутствующий id даёт `memory_error`.
- История берётся через `MemoryService.prepare_context()` с ограничением
  сообщений и символов; флаг `context_truncated` показывает обрезку.
- Сниппеты долговременной памяти добавляются только по явному
  `memory_query` (максимум 5), как данные, а не инструкции.
- Автоматического запоминания нет: каждая фраза в долговременную память
  не пишется.
- При `memory.enabled = false` ход работает без истории:
  `memory_enabled=False`, `persisted=False`.
- Если сохранение не удалось, ответ всё равно возвращается, но
  `persisted=False` и `persist_error` заполнен — история не считается
  сохранённой.
- Результат инструмента передаётся модели сообщением роли `tool` с
  префиксом «data, not instructions».

## 7. Подтверждение и возобновление

```
send() -> approval_required + pending_id
approve_pending(pending_id) -> grant (bound to tool+version+digest)
                            -> execute once -> resume loop -> success
cancel_pending(pending_id)  -> отказаться, ничего не выполняя
pending()                   -> список ожидающих (без значений аргументов)
```

Ожидающих ходов хранится не более 8, просроченные удаляются
(`pending_ttl_seconds`, по умолчанию 300 с). Подтверждение выдаёт только
`approve_pending()` — путь доверенного интерфейса (CLI/UI), никогда ответ
модели.

## 8. Конфигурация `[orchestration]`

```toml
[orchestration]
enabled = true
max_tool_calls_per_message = 3        # 0..10
allow_text_tool_calls = false         # не угадывать вызовы из прозы
persist_history = true
pending_ttl_seconds = 300.0
```

Env: `JARVIS_ORCHESTRATION_ENABLED`, `JARVIS_ORCHESTRATION_MAX_TOOL_CALLS`,
`JARVIS_ORCHESTRATION_ALLOW_TEXT_CALLS`, `JARVIS_ORCHESTRATION_PERSIST`.
Валидация отклоняет отрицательный и чрезмерный лимит, а также
неположительный TTL.

## 9. CLI

```bash
python -m jarvis --dialog-send "Сколько будет 2+40?"
python -m jarvis --dialog-send "ещё" --dialog-conversation conv_...
python -m jarvis --dialog-send "..." --dialog-system "Ты — JARVIS"
python -m jarvis --dialog-pending                 # ожидающие подтверждения

```

Коды выхода: `0` — норма, `2` — уже запущен другой экземпляр, `3` —
конфигурация, `4` — AI, `5` — память, `6` — инструмент, `7` — диалог
(любой статус кроме `success`). Интерактивного бесконечного цикла нет:
один вызов — один ход.

## 13. Приватность и границы защиты

- В логи идут идентификаторы, статусы и счётчики — не текст сообщений и не
  значения аргументов. Ожидающее подтверждение печатается пользователю
  вместе с аргументами (для осознанного согласия), но `describe()` и
  аудит инструментов значений не содержат.
- Ответ модели, описание инструмента, содержимое памяти и результат
  инструмента считаются данными, а не инструкциями.
- Нет произвольного запуска команд, нет `eval`, нет скрытых фоновых
  агентов, нет автономного планирования.
- Сеть не используется при старте; явный ход идёт к провайдеру только при
  настроенной модели.
- **Подтверждение не является защитой ОС.** Политика работает внутри
  процесса JARVIS: она не ограничивает другие программы, не песочница, и
  не защищает от инструмента, который уже получил разрешение.

## 15. Ограничения

- Нет потоковой выдачи ответа наружу: ход использует `generate()`, не
  `stream()`. Стриминг остаётся доступным в AI-слое.
- Нет автономного агента, планировщика и фоновых задач: один вызов — один
  ограниченный ход.
- Текстовый канал вызова инструмента по умолчанию выключен: вызов возможен
  только через структурированный канал, который провайдеры Ollama и
  OpenAI-compatible заполняют из своего поля `tool_calls`.
- Нативные вызовы инструментов не агрегируются в потоковой выдаче:
  `stream()` отдаёт только текст (ход диалога использует `generate()`).
- Ожидающие подтверждения живут только в памяти процесса: после перезапуска
  их нужно запросить заново.
- Отмена хода кооперативная: она останавливает ход между шагами, но **не
  прерывает уже запущенный инструмент** — такой ход возвращает `cancelled` и
  перечисляет выполненные вызовы, не создавая иллюзии «ничего не было».
- Интерфейс есть и закрывает согласованный объём Фазы 6 (окно, диалог,
  подтверждения, отмена, экспорт, история с пагинацией, настройки,
  диагностика); нет голоса, браузерной автоматизации, зрения, маркетплейса и
  подписок — это отдельные фазы, а не «почти готовое».
- Экспорт — один диалог в JSON через существующий `MemoryService`; выгрузки
  «всей памяти одним файлом» нет.
- Single-instance — по-прежнему файловый lock (не Win32-mutex).
- Ожидающие подтверждения вытесняются при переполнении (старше
  `MAX_PENDING_TURNS`): теперь это событие пишется в лог, но сам факт
  вытеснения остаётся — повторный запрос нужен.

### 20.5 Найденный и исправленный дефект (реальный прогон GUI)

При первом реальном запуске окна ход выполнился в фоновом потоке, а экспорт и
чтение истории — в потоке интерфейса. Проявилось:
`SQLite objects created in a thread can only be used in that same thread`,
затем `InterfaceError: bad parameter or other API misuse`.

Исправлено в `jarvis/memory/database.py`: **соединение на поток**
(`threading.local` + реестр соединений), `close()` закрывает все; конкурентность
на уровне файла обеспечивает сам SQLite (WAL, один писатель, `timeout`).
Покрыто двумя тестами в `tests/memory/test_service.py`.

### 20.6 EventBus

Добавлен `threading.RLock`: `subscribe`, `unsubscribe`, `clear`, `handlers` и
запись сбоев — под блокировкой; обработчики вызываются **вне** блокировки,
чтобы медленный обработчик не блокировал регистрацию. Проверено тестами:
8 потоков × 50 публикаций → 400 доставок без потерь; подписка во время
публикации не ломает шину.

Ограничение зафиксировано честно: блокируется только реестр обработчиков и
журнал сбоев; сами обработчики обязаны быть быстрыми и реентерабельными.

### 24.2 Разделение фактов (главное правило фазы)

- **implemented** — класс существует (`windows_sapi_tts`, `windows_sapi_stt`).
- **configured** — настройки заданы (`voice.*`).
- **available** — решает проба системы, а не наличие класса; `status(probe=False)`
  честно отвечает «не проверено».
- **blocked** — `InstalledRecognizers=0` для STT в этой системе.
- **actually tested (hardware)** — TTS: да, рендер в память; STT: нет.

### 24.4 Найденные и исправленные дефекты

1. `_finish()` в сессии пересобирала `VoiceTurn` и **теряла** поля `pending /
   pending_tool / pending_id` — голосовой запрос инструмента с требованием

   Заменён на `_spawn`, покрыт UI-тестами.
3. Кнопка «Слушать» была активной при живом TTS, даже без распознавателя:

5. `status()` без пробы молча вызывал PowerShell внутри UI-кадра; теперь проба
   явная и выносится в рабочий поток моста (`probe_voice()`).
6. NO_SPEECH трактовался как ошибка бэкенда; теперь это честный пустой transcript
   (ход не отправляется).

### 24.5 Безопасность и приватность

- Audio не сохраняется, не логируется и никуда не уходит; diagnostics не пишет БД.
- По умолчанию `voice.privacy = local_only` и `voice.allow_remote = false`;
  неизвестный режим приватности отклоняется конфигом и роутером.
- Голосовая команда не имеет привилегий: tool call идёт через ToolSystem,
  `echo_text` останавливается на подтверждении, неизвестный инструмент
  отклоняется (покрыто интеграционными тестами).
- Отмена кооперативная: останавливает действия между шагами и завершает **свой**
  дочерний процесс PowerShell; уже произнесённое не «отменяется».
- Никаких автоматических retry, автоматического прослушивания или озвучивания:
  всё только по явному действию пользователя.
